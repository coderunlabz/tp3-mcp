# Especificação MCP 2026-07-28 — resumo

Resumo próprio, em português, de quatro páginas da especificação oficial: visão geral, arquitetura, transportes e lista de mudanças. Acessadas em 01/10/2026. Não é cópia do texto; termos entre crases são os nomes oficiais.

- Seções: Visão geral, Arquitetura, Transportes, Mudanças desta revisão, Depreciações, Fontes.

## Visão geral

MCP é um protocolo aberto para ligar aplicações de IA a dados e ferramentas externas. As mensagens usam JSON-RPC 2.0. A base é de pedidos sem estado e autocontidos, com negociação de capacidades a cada pedido.

Servidores oferecem três coisas: resources (contexto e dados, para a pessoa ou para o modelo), prompts (mensagens-modelo para a pessoa) e tools (funções que o modelo executa). Clientes podem oferecer elicitation (o servidor pedir mais informação à pessoa). Extensões opcionais, que exigem suporte dos dois lados: Tasks, Skills over MCP e MCP Apps.

A página compara a ideia ao Language Server Protocol: assim como ele padroniza o suporte a linguagens nas ferramentas de desenvolvimento, o MCP padroniza a entrada de contexto e ferramentas nas aplicações de IA.

Segurança: a página lista consentimento e controle da pessoa, privacidade de dados e cuidado com tools, que são execução arbitrária de código. Descrições de tools devem ser tratadas como não confiáveis, salvo vindas de servidor confiável. O protocolo não impõe isso sozinho; quem implementa precisa construir.

## Arquitetura

Modelo cliente–host–servidor. O host é o aplicativo que cria e coordena os clientes, controla permissões e consentimento e agrega o contexto. Cada cliente é criado pelo host e fala com exatamente um servidor. Servidores expõem resources, tools e prompts, podem ser processos locais ou serviços remotos.

Princípios de projeto: servidores fáceis de construir; compostos entre si; sem poder ler a conversa inteira nem "ver dentro" de outros servidores; recursos adicionados aos poucos.

Capacidades: o cliente manda as suas em `_meta.io.modelcontextprotocol/clientCapabilities` a cada pedido; o servidor as anuncia em resposta a `server/discover`, que o cliente pode chamar antes de qualquer outro pedido.

## Transportes

Transporte é uma ligação: define como as mensagens são entregues, não o que significam. Dois padrão:

1. stdio: mensagens separadas por linha, nos fluxos padrão de um subprocesso iniciado pelo cliente.
2. Streamable HTTP: cada mensagem é um POST para um endpoint único; a resposta vem como objeto JSON ou como stream SSE restrito àquele pedido.

Todo metadado do protocolo vai no corpo. O Streamable HTTP espelha alguns campos em cabeçalhos para intermediários roteirizarem sem abrir o corpo; o corpo continua sendo a fonte de verdade. Cancelamento: no stdio, uma notificação `notifications/cancelled`; no HTTP, fechar o stream da resposta. Servidores não iniciam pedidos JSON-RPC e clientes não mandam respostas.

## Mudanças desta revisão (frente a 2025-11-25)

Removidas:
- sessão de protocolo e cabeçalho `Mcp-Session-Id`;
- handshake `initialize`/`notifications/initialized`;
- retomada de stream SSE (`Last-Event-ID`): um stream quebrado perde o pedido em andamento, e o cliente precisa refazê-lo com novo id;
- `ping`, `logging/setLevel` e `notifications/roots/list_changed`;
- `notifications/elicitation/complete` e o campo `elicitationId`.

Adicionadas:
- cada pedido leva versão do protocolo e capacidades do cliente no `_meta`; clientes devem se identificar (`clientInfo`) e servidores também (`serverInfo`);
- `server/discover`: servidores devem implementar; clientes podem chamar;
- `subscriptions/listen`: um único stream para avisos de mudança, com adesão por tipo;
- Multi Round-Trip Requests: o servidor devolve `resultType: "input_required"` com `inputRequests`, e o cliente refaz o pedido com `inputResponses`. Todo resultado agora traz `resultType`;
- cabeçalhos `Mcp-Method` e `Mcp-Name` obrigatórios em POST;
- `ttlMs` e `cacheScope` em resultados de listas e leitura de recurso; ordem determinística em `tools/list` (recomendada);
- campo `extensions` nas capacidades; Tasks vira extensão oficial (`io.modelcontextprotocol/tasks`);
- código de erro de recurso inexistente passa de `-32002` para `-32602`;
- `inputSchema` e `outputSchema` aceitam JSON Schema 2020-12 completo;
- endurecimento de autorização: validação de `iss` (RFC 9207), `application_type` no registro dinâmico, credenciais presas ao emissor.

## Depreciações (janela mínima de 12 meses)

Roots, Sampling e Logging; transporte HTTP+SSE antigo; valores `thisServer` e `allServers` de `includeContext`; registro dinâmico de cliente (RFC 7591), em favor de Client ID Metadata Documents. Política formal: estados Ativo, Depreciado e Removido, com registro público do que está depreciado.
